# Наряд №009 — OCR экранного текста для отобранных кадров

**Волна:** 1 (Индексатор)  
**Стадия:** indexer  
**Размер:** M  
**Исполнитель:** agent  
**Зависит от:** #33, #6  
**Связанные ADR:** —  
**Статус:** open

## Контекст
Во многих рецептах ингредиенты и шаги показаны только текстом на экране. Распознавание идёт через VLM или облачный OCR (слой провайдеров), но не для всех кадров, чтобы не тратить деньги.

## Контракт
```
frames.json + frames/*.jpg
→ ocr.json: [{frame, t, text, lang}] — только для кадров, прошедших фильтр «вероятно есть текст»; одинаковый текст на соседних кадрах схлопнут
```

## Scope
- Фильтр кандидатов: ключевые кадры сцен и кадры с высокой плотностью границ (дёшево, на CPU), лимит `max_ocr_frames` в конфигурации.
- Вызов провайдера пакетами, кэш по хэшу кадра, учёт стоимости.
- Схлопывание повторяющегося текста на последовательных кадрах (сохранить интервал времени).

## Non-goals
- Реальный адаптер (№39).
- Структурный разбор списка ингредиентов (волна 3).

## Acceptance criteria
- [ ] На `titles.mp4` с fake-VLM, возвращающим текст из `ground_truth.json`, все строки найдены с верным временем (допуск ±1 с)
- [ ] Число вызовов провайдера не превышает `max_ocr_frames`; доля кадров, отправленных на OCR, выводится в итоге стадии
- [ ] `ocr.json` валиден по схеме из №35
- [ ] CI зелёный

## Assumptions / Open questions
- Порог плотности границ подбирается на эталонном наборе (шлюз B).

## Проверка аудитора
- Проверить, что при нулевом лимите стадия работает и пишет пустой результат.
- Проверить, что дубли схлопываются и не теряют интервал времени.
