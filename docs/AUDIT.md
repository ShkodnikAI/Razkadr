# Аудит: как принимаются PR и шлюзы

Аудитор не верит отчётам: проверяет запуском.

## Режим работы: автомёрж, аудит после
PR наряда мёржатся автоматически при зелёном CI и выполненных формальных условиях (`scripts/ci/automerge.py`). Аудитор не блокирует мёрж, а проверяет принятое **постфактум**: чем больше качество держится на тестах, тем важнее раздел ниже. Найденный дефект оформляется новым нарядом (исправление) с приоритетом перед зависимыми. Остановки только по решению владельца: метка `needs-owner`, защищённые пути, шлюзы.

Аудит принятых PR выполняется по запросу владельца и обязательно перед каждым шлюзом: аудитор проходит по всем мёрж-коммитам волны по списку ниже.

## Проверка принятого PR (наряд)
1. **Привязка:** `Closes #NNN`, номер наряда совпадает с содержимым, зависимости наряда закрыты.
2. **Диф в пределах scope:** нет посторонних изменений; изменения схем, ADR и чужих интерфейсов — только если разрешены нарядом.
3. **Запуск самому:** checkout ветки, `pip install -e ".[dev]"`, `ruff check .`, `pytest`, затем пример из контракта наряда руками. Результат сверить с заявленным в PR.
4. **Acceptance criteria:** каждый пункт проверен отдельно; пустые пункты в PR — причина возврата, если не объяснены.
5. **Тесты осмысленные:** ловят нарушения, а не только проходят (мутация: сломать поведение и убедиться, что тест падает — для ключевых нарядов).
6. **Безопасность:** поиск ключей/токенов в диффе и артефактах; новые зависимости оправданы и перечислены; сеть в тестах отсутствует.
7. **Числа:** любое число в PR воспроизводится командой из PR.
8. **Assumptions и Unresolved:** прочитаны; необходимое вынесено в новые наряды или вопросы владельцу.
9. **Решение:** принят / дефект. Дефект оформляется нарядом-исправлением (или откатом коммита, если сломан `main`).

В каждом наряде есть раздел «Проверка аудитора» — дополнительные специфичные проверки.

## Приёмка шлюза
1. Все наряды волны закрыты и приняты.
2. Аудитор сам запускает проверки из файла шлюза и заполняет `docs/acceptance/wave-N.md` (шаблон `TEMPLATE.md`) числами из своих запусков.
3. Критерии, требующие владельца (демонстрация, оценка, ключи), отмечены явно.
4. Рекомендация go / go с замечаниями / no-go с обоснованием; решает владелец.
5. После go аудитор уточняет черновики следующей волны (снимает метку `draft`).

## Возврат и эскалация
- Возврат: комментарий с нумерованным списком замечаний, ссылки на строки/команды.
- Два возврата подряд по одному наряду: аудитор пересматривает формулировку наряда (возможно, контракт неоднозначен).
- Нужно изменить принятый ADR или схему: вопрос владельцу, не агенту.
