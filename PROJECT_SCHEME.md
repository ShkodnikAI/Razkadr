# Схема работы над проектом

> Один раз зафиксировать процесс, дальше не объяснять заново. Все роли работают строго по этой схеме.

## Роли

| Роль | Кто | Что делает |
|---|---|---|
| **Владелец** | человек | Цели и приоритеты, API-ключи, эталонные видео, решения на шлюзах (go / no-go), принятие ADR |
| **Аудитор** | Claude (этот чат) | Пишет наряды (issues) и критерии, ведёт ADR-черновики, принимает PR и шлюзы по `docs/AUDIT.md`. Код продукта не пишет |
| **Агент-кодер** | отдельный кодирующий агент | Берёт наряд, реализует, открывает PR. Правила: `AGENTS.md` |

Поток: аудитор выдаёт наряды (issues) → автоматика ставит `ready` нарядам с закрытыми зависимостями → агент берёт наряд и открывает PR → при зелёном CI PR мёржится автоматически, issue закрывается, `ready` получают следующие → аудитор проверяет принятое (перед шлюзом и по запросу) → после всех нарядов волны аудитор готовит протокол шлюза → владелец решает.

Автоматика: `.github/workflows/orchestrate.yml` (мёрж, раздача, ежечасная страховка). Метки: `ready` — можно брать, `in-progress` — взят, `needs-owner` — ждёт владельца, `draft` — контракт не готов.

## Единицы работы

| Единица | Что это | Где |
|---|---|---|
| **Наряд** | Атомарная задача с контрактом (вход → ожидаемый выход, scope, non-goals). Номер наряда = номер issue | `docs/naryady/NNN-*.md` + GitHub Issue + PR |
| **ADR** | Архитектурное решение (accepted / rejected / deferred) | `docs/adr/` |
| **Волна** | Группа нарядов с одной целью и шлюзом приёмки | `docs/PLAN.md` |
| **Шлюз** | Приёмка промежуточного результата волны: проверяемые критерии, go / no-go | `docs/naryady/042…047-gate-*.md`, issues #42–47 |

## Цикл наряда

1. **Sync:** `git fetch origin main && git reset --hard origin/main` (на чистой ветке).
2. **Факты, а не prose:** перед действием проверить код или реальный запуск. README и ADR могут отставать.
3. **Реализация:** Conventional Commits, один логический шаг ≈ один коммит.
4. **Delivery = «наряд сделан»:** ветка запушена, PR открыт (`Closes #NNN`), проверки зелёные, в отчёте явные assumptions и unresolved.
5. **После merge** (автоматически): issue закрыт, ветка удалена, следующим нарядам выставлен `ready`. При архитектурном решении агент готовит ADR proposed: такой PR ждёт владельца.

## Приёмка волны

1. Все наряды волны в статусе `done`.
2. Шлюз проходится по чек-листу из `docs/PLAN.md`: проверяемые метрики и демонстрация владельцу проекта.
3. Результат фиксируется в `docs/acceptance/wave-N.md` (дата, метрики, решение: go / go с замечаниями / no-go).
4. При no-go: наряды на исправление создаются в той же волне, следующая волна не стартует.

## Источники истины

| Вопрос | Смотреть сюда |
|---|---|
| Существует ли X / как работает | код, а не README |
| Текущие ограничения | `docs/limitations.md` |
| Почему так решили | `docs/adr/` |
| Что считается «готово» | чек-лист наряда + шлюз волны |

## Правила для AI-агента

- Работать строго по этой схеме.
- Не менять принятые ADR без явного запроса владельца.
- Перед стартом наряда: sync и проверка фактов.
- В отчёте всегда указывать assumptions и unresolved.
- Не расширять scope наряда; найденное вне scope оформлять отдельным нарядом.
- Не выдумывать метрики: любое число в отчёте получено запуском.

## Сознательно упрощено

Нет множества blocking CI jobs с нуля (добавляются по мере роста), нет формального feature-intake, нет пула good-first-issue (нет внешних контрибьюторов).
