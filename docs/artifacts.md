# Артефакты стадий и каталог запуска

Каждый запуск конвейера живёт в собственном каталоге `runs/<run_id>/`. Стадия читает артефакты предыдущих и пишет свои; форматы зафиксированы JSON Schema (draft 2020-12), файлы схем — `schemas/<kind>.v1.json`, копии поставляются с пакетом (`src/razkadr/schemas/`, синхронность проверяет тест). Зафиксировав форматы до реализации стадий, можно разрабатывать и принимать стадии независимо (наряды №5–11).

- Валидация: `razkadr validate --kind <kind> <файл>`; без `--kind` файл проверяется как Storyboard (наряд №002).
- Виды: `storyboard`, `source`, `frames`, `transcript`, `chunks`, `ocr`, `index`, `run`. Отдельный вид `eval_labels` — разметка эталонного набора (`data/eval/labels/<id>.json`, наряд №003): это не артефакт стадии, целостность всего набора проверяет `razkadr eval-check data/eval` (см. `data/eval/README.md`).
- Примеры: `examples/artifacts/` — по одному небольшому валидному примеру на каждый артефакт.
- Каждая схема несёт `schema_version` (semver, см. «Совместимость»).

## Структура каталога запуска

```
runs/<run_id>/
  run.json            # run: версии, конфиг-хэш, стадии, вызовы провайдеров, сводка  (kind=run)
  source.json         # source: путь/URL, sha256, длительность, fps, разрешение, дорожки (kind=source)
  normalized.mp4      # нормализованное видео (пишет ingest)
  audio.wav           # аудиодорожка для ASR (пишет ingest)
  frames/
    *.jpg             # выбранные кадры
    ../frames.json    # frames: t, file, scene_id, sharpness, phash, exposure; rejected+reject_reason для отбракованных (kind=frames)
  transcript.json     # transcript: сегменты (t_start, t_end, text, lang, speaker?) + язык (kind=transcript)
  chunks.json         # chunks: тематические чанки (id, t_start, t_end, text, lang, segment_ids — привязка к сегментам транскрипта) (kind=chunks)
  ocr.json            # ocr: текст на кадрах (frame, t, text, lang) (kind=ocr)
  index/
    manifest.json     # index: провайдер, модель, версия, dim, число векторов (kind=index)
    vectors.bin       # payload векторов; путь фиксируется в manifest.vectors_file
    meta.db           # SQLite: id/space/метаданные векторов + meta (dim, provider, model, version)
  storyboard.json     # storyboard (наряд №002): черновик создаётся отбором (волна 2),
                      #   стадия text (волна 3) заполняет episodes[].text, отчёт — text.json
  select.json         # отчёт отбора (наряд №014): запросы, скоринг, предупреждения
  slides.json         # slides (наряд №021): макеты слотов и предупреждения раскладки
  deck.pptx           # PPTX-дека на шаблоне (наряд №022), спикерские заметки из Storyboard
  deck.pdf            # PDF деки через LibreOffice headless (наряд №024)
  deck.html           # самодостаточная HTML-дека с таймкод-ссылками (наряд №026)
  deck_assets/        # кадры для HTML-деки
```

`run_id` — имя каталога и поле `run_id` в `run.json` (одинаковые). Пути внутри артефактов (`frames[].file`, `vectors_file`) задаются относительно каталога запуска: каталог можно перемещать целиком.

### Пакет команды build (наряд №028)

`razkadr build` — сквозной запуск: индекс (№005–011) → отбор (№014) → текст (№017/018) → раскладка (№021) → рендер (№022) → HTML (№026) → PDF (№024). Пакет результатов живёт в каталоге запуска (или в `--out-dir`): `deck.pptx`, `deck.pdf`, `deck.html` (+ `deck_assets/`) и `storyboard.json` — валидированный Storyboard с текстами и есть JSON-артефакт пакета.

Кэш и возобновление наследуются от стадий: layout/render/html/pdf пишут маркеры кэша по фингерпринтам содержимого (storyboard → slides → deck), поэтому `--resume` после сбоя не пере-рендерит то, что не менялось; отбор и текст выполняются повторно, но идемпотентны (правки пользователя сохраняются, вызовы провайдеров отдаются из кэша вызовов). Без LibreOffice (soffice) в PATH пакет уходит без PDF с предупреждением в stderr, остальные артефакты не затронуты; без шаблона пользователя используется эталонный `templates/razkadr-default.pptx`.

## Индекс (№010): хранилище векторов

Стадия читает `frames.json` (только не-отбракованные кадры), `chunks.json`
и `ocr.json`, считает эмбеддинги через слой провайдеров (`[embeddings]`,
батчами по `batch_size`, каждый батч кэшируется) и пишет:

- `index/vectors.bin` — матрица float32 N×dim (строки в порядке `vectors.row`);
- `index/meta.db` — SQLite: таблица `vectors` (id, space, row, source, file,
  t, t_end, scene_id, sharpness, lang, text) и таблица `meta` (dim, provider,
  model, version);
- `index/manifest.json` — по схеме `index.v1.json`: провайдер, модель, версия,
  dim, num_vectors, `vectors_file` (путь относительно каталога запуска).
  Поле `space` не заполняется: хранилище смешивает три пространства —
  `frames` (кадры), `chunks` (тексты чанков), `ocr` (распознанные тексты);
  пространство каждой записи — в столбце `space`.

Поиск — точный по косинусной близости (numpy, ADR-0007, proposed):
`LocalVectorStore(dir).open().search(query, k, filters)` → `[(id, score,
metadata)]`, порядок — по убыванию score, при равенстве по id. Фильтры
(`Filters`, все опциональные, комбинируются через AND): `spaces` —
подмножество {frames, chunks, ocr}; `source` — точное совпадение (url или
путь из `source.json`); `t_start`/`t_end` — пересечение временного интервала
(кадры/OCR — мгновение t, чанки — отрезок t_start..t_end);
`min_sharpness` — только кадры (текстовые записи без резкости отсекаются).

Смена провайдера, модели или `model_version` меняет ключ кэша стадии —
индекс пересобирается с нуля (`index/` стирается), смена помечается в логе
(`index is stale`). При полностью пустом входе (нет принятых кадров, чанков
и OCR) размерность берётся одним пробным вызовом `embed_texts` (вектор не
сохраняется). Без раздела `[embeddings]` стадия пропускается с предупреждением
и артефакты `index/` не создаются.

## Что пишет и читает каждая стадия

| Стадия (наряд) | Читает | Пишет |
|---|---|---|
| Ingest (№005) | исходный файл или URL | `source.json`, `normalized.mp4`, `audio.wav` |
| Кадры (№006) | `normalized.mp4` | `frames/*.jpg`, `frames.json` |
| Транскрипт (№007) | `audio.wav` | `transcript.json` |
| Чанки (№008) | `transcript.json` | `chunks.json` |
| OCR (№009) | `frames.json`, `frames/*.jpg` | `ocr.json` |
| Индекс (№010) | `frames.json`, `chunks.json`, `ocr.json`, `source.json` | `index/manifest.json`, `index/vectors.bin`, `index/meta.db` |
| Отбор (№014, волна 2) | `index/`, `frames.json`, `chunks.json`, `ocr.json` | `storyboard.json` (черновик без текста) |
| Текст (№017–019, волна 3) | `storyboard.json`, `transcript.json` | `storyboard.json` (с текстом) |
| Сборка (№021–028, волна 4) | `storyboard.json`, кадры | PPTX/PDF/HTML/JSON |
| RunContext (№036) | — | `run.json`, кэш вызовов, логи |

## Схема зависимостей стадий

```
Ingest ──→ Кадры ──┬──→ OCR ────┐
   │               │            ├──→ Индекс ──→ Отбор ──→ Текст ──→ Сборка
   ├──→ Транскрипт ┴→ Чанки ────┘           (Storyboard: черновик → с текстом)
   └────────── RunContext ведёт run.json через все стадии
```

Порядок «Кадры/Транскрипт → Чанки → OCR → Индекс» параллелится на независимых ветках (Кадры и Транскрипт не зависят друг от друга). Каждая стрелка = ссылка на артефакт из таблицы выше; стадии не общаются иначе, кроме как через артефакты в каталоге запуска.

## Формат run.json — учёт вызовов провайдеров

`run.json` ведёт RunContext (наряд №036). Запись `provider_calls[]` обязательными полями фиксирует: `stage`, `provider`, `model`, `units[]` (`kind`: `seconds|tokens|images`, `value`), `cost` (`amount`, `currency` ISO 4217, `tariff_date`), `cache_hit` — этого достаточно, чтобы на шлюзе B посчитать стоимость минуты видео и долю попаданий в кэш без доступа к провайдерам. Один вызов может занимать несколько единиц (VLM: `images` + `tokens`). Ключи API в `run.json` и прочих артефактах запрещены (см. `AGENTS.md` и наряд №033).

Стадии в `stages[]`: `name`, `status` (`ok|failed|skipped|cached`), опционально `started_utc`, `duration_s`, `error` (для `failed`). Статус `cached` означает: артефакт взят из предыдущего запуска без повторных платных вызовов.

## Итоговая сводка и возобновление (№011)

После успешного завершения всех стадий команда `razkadr index` дописывает в `run.json` блок `summary` (схема `run.v1.1`, поле необязательное):

- `stage_times_s` — реальное время каждой стадии, секунды; берётся последняя завершённая попытка стадии в этом запуске (неудачные попытки без `duration_s` не учитываются);
- `provider_cost` — `provider_calls[]` агрегированы: `amount` (сумма), `currency` (ISO 4217 всех вызовов; отсутствует, когда вызовов не было), `calls`, `cache_hits`, `by_stage` (стоимость по стадиям);
- `artifacts` — ключевые числа артефактов: `frames_candidates`, `frames_accepted`, `frames_rejected`, `ocr_results`, `ocr_frames_sent`, `transcript_segments`, `transcript_s` (секунды речи, покрытые сегментами), `chunks`, `index_vectors`.

Сводка пишется один раз; у упавшего запуска блока `summary` нет — для диагностики достаточно лога стадий и вызовов. Консоль печатает те же числа строками `cost:` и `time:`.

Возобновление: сбой стадии печатает имя стадии и подсказку `razkadr index <вход> --resume <run_id>`. Повторный запуск с `--resume` продолжает с упавшей стадии: завершённые стадии по кэш-маркерам `.cache/<stage>.json` читают артефакты с диска (статус `cached`, ни одного нового вызова провайдеров), упавшая выполняется заново. История стадий в `stages[]` дописывается (`ok, …, failed, cached, …, ok`) — по ней видно весь ход запуска. Смена конфига, провайдера или входного файла меняет ключ стадии — она честно пересчитается. `--resume` с несуществующим `run_id` — ошибка, а не молчаливый новый запуск.

Устойчивость к обрыву (№029): маркер кэша пишется после тела стадии, а все JSON-артефакты и файлы деки (PPTX/PDF/HTML) кладутся на диск атомарно (tmp + `os.replace` в том же каталоге, модуль `razkadr/atomicio.py`). Поэтому жёсткий обрыв (SIGKILL, потеря питания) посреди стадии оставляет воспроизводимое состояние: артефакт либо отсутствует, либо полный; повторный запуск с `--resume` пересчитывает только стадию без маркера и перезаписывает её выход целиком. Битый артефакт при актуальном маркере (повреждение диска, ручная правка) — чистая ошибка с двумя лекарствами: `--force` для пересчёта или удалить файл; traceback'а нет. Полная матрица форм аварии покрыта тестами `tests/test_resume.py` (реальный SIGKILL посреди стадии, обрезанный файл без маркера, битый файл с маркером).

## Правила совместимости

- Версия артефакта — `schema_version` в самом файле, semver (`1.0` ≡ `1.0.0`); валидатор принимает только свою major-версию и отвергает чужую с понятным сообщением.
- **MINOR** — новые необязательные поля или новые значения enum: старый код читает новый файл; стадии обязаны игнорировать неизвестные поля, а не падать.
- **MAJOR** — несовместимые изменения: новый файл схемы `schemas/<kind>.v2.json`, мигратор, обновление всех стадий, пишущих/читающих вид.
- Семантические проверки сверх схем: уникальность `id` и `t_end >= t_start` для `chunks`/`transcript`/`episodes` Storyboard; время в пределах `duration_s` источника — для Storyboard; major-версия — для всех видов. Всё остальное — уровень схемы, без «свободных» полей (`additionalProperties: false` везде, кроме описанных в схемах исключений).
- Проверки дат (`created_utc`, `started_utc`, `tariff_date`) синтаксические (ISO 8601): календарная валидность (например, 32 января) схемой не отвергается — осознанное упрощение, чтобы не добавлять зависимости от rfc3339-валидатора.
- sha256 в `source.json` — хэш файла `path` (нормализованного видео): это ключ кэша для всех стадий; смена источника меняет хэш и инвалидирует кэш запуска.

## Связь со Storyboard

`storyboard.json` в каталоге запуска подчиняется схеме `storyboard.v1.json` (наряд №002, описание — `docs/storyboard.md`). Storyboard — единственный артефакт, который пользователь правит руками; стадии обязаны сохранять пользовательские правки (`user_edited`).
