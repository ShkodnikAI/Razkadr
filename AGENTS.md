# Инструкция для агента-кодера

Ты реализуешь наряды проекта Razkadr. Прочитай целиком до начала работы, затем читай только свой наряд.

## Что читать
1. Свой issue (наряд): контракт, scope, non-goals, acceptance criteria. Это единственный источник требований.
2. `docs/spec.md` — только разделы, на которые ссылается наряд. `docs/adr/` — принятые решения (accepted) менять нельзя.
3. `PROJECT_SCHEME.md` — процесс.

## Как работать
1. Берёшь issue с меткой `ready` (наименьший номер). Метку ставит автоматика, когда все зависимости закрыты; наряды `draft` и `needs-owner` не бери. Сразу при старте: убери `ready`, поставь `in-progress`, оставь комментарий «взял».
2. Ветка от свежего `main`: `git fetch origin main`, ветка `naryad/NNN-кратко`.
3. Сначала проверь факты в коде, затем пиши. README и документы могут отставать.
4. Conventional Commits; один логический шаг — один коммит.
5. Тесты вместе с кодом. Сеть и реальные ключи в тестах CI не используются: только fake-провайдеры и фикстуры (наряд №34). Тесты с реальным провайдером помечай `live` и пропускай без ключа.
6. `ruff check .` и `pytest` проходят локально до пуша.
7. PR из шаблона: `Closes #NNN`, что сделано, проверка (команды и вывод), чек-лист acceptance наряда, **Assumptions**, **Unresolved**.

## Жёсткие правила
- Не выходи за scope. Найденное вне scope — в Unresolved (аудитор оформит отдельный наряд).
- Не меняй принятые ADR, схемы (`schemas/`) и интерфейсы чужих нарядов без явного пункта в наряде. Если без этого нельзя — остановись и опиши в PR/issue.
- Никаких выдуманных чисел: любое число (время, стоимость, метрика) получено запуском, команда указана.
- Секреты: ключи только из окружения; не логируй, не коммить, не клади в `run.json`, фикстуры и тестовые ответы.
- Не коммить видео, ключи, `runs/`, кэш. Данные эталона — вне git.
- Не отмечай acceptance-пункт выполненным без проверки. Не удалось — оставь пустым и объясни.
- Не пушь в `main` и не мёржи сам. Мёрж автоматический: при зелёном CI, наличии `Closes #N`, разделов Assumptions и Unresolved, при ветке не отстающей от main и без конфликтов. После мёржа issue закрывается, автоматика ставит `ready` следующим нарядам.
- Ветка называется `naryad/NNN-кратко`, иначе автомёрж не сработает.
- Не меняй `docs/adr/`, `.github/`, `scripts/ci/`, `AGENTS.md`, `LICENSE`, `PROJECT_SCHEME.md`, `docs/AUDIT.md` без явного пункта в наряде: такой PR автоматически останавливается до решения владельца (метка `needs-owner`).
- Если ветка отстаёт от `main` или есть конфликт — сделай rebase и запушь.

## Если нужно решение владельца
Не угадывай. Поставь на issue (и на PR, если он есть) метку `needs-owner`, напиши в комментарии вопрос и варианты, сними `in-progress`. Затем **не жди**: возьми следующий `ready` наряд. Автомёрж останавливается на таком PR, а зависимые от него наряды останутся заблокированными, независимые продолжатся. Владелец снимает метку, когда решит.

## Вопросы в рамках наряда без решения владельца
Неоднозначность, которую можно разрешить разумным допущением, не повод останавливаться: прими допущение и запиши в Assumptions.
