# План реализации Razkadr

Статус документа: v1, 2026-10-15. Основа: [spec.md](spec.md) v0.4. Процесс: [../PROJECT_SCHEME.md](../PROJECT_SCHEME.md).

## 0. Как читать план

- **Наряд** — атомарная задача с контрактом. Размер: S (до дня), M (несколько дней), L (до недели и больше). Это ориентир сложности, а не обещание по срокам: реальные сроки уточняются после замеров на волне 0.
- **Волна** — группа нарядов с единой целью. Следующая волна стартует только после **шлюза** (приёмки) предыдущей.
- **Шлюз** — проверяемые критерии и демонстрация владельцу. Результат записывается в `docs/acceptance/wave-N.md` по шаблону `docs/acceptance/TEMPLATE.md`. Решение: **go / go с замечаниями / no-go**.
- Пороговые значения помечены «предложено»: их можно корректировать на предыдущем шлюзе, но только осознанно и с записью в протокол.
- Подробно расписаны волны 0–5 (ядро до MVP-результата). Волны 6+ только обозначены и детализируются после шлюза F.

## 1. Сквозные принципы

1. **Контракт раньше кода.** Схема Storyboard и формат разметки эталона фиксируются в волне 0.
2. **Метрики раньше сравнений.** Любое «лучше» (модель, поиск, скоринг) подтверждается на размеченном наборе, не «на глаз».
3. **Python-only до веб-оболочки** (ADR-0001). Металогос не является зависимостью.
4. **Модели только внешние (API), с поддержкой BYOK** (ADR-0004). Локальных моделей нет; на CPU остаются ffmpeg, детекция сцен, хэши и рендер. Платные вызовы выполняются после дешёвой отбраковки и кэшируются.
5. **Минимум реализаций за полными контрактами:** 1 пресет (`recipe`), 2–3 макета, 2 языка вывода (RU, EN).
6. **PPTX — мастер-формат** (ADR-0003): PDF и Google Slides получаются из него.
7. **Воспроизводимость и учёт стоимости:** каждый запуск пишет `run.json` (провайдеры и версии моделей, параметры, время и стоимость вызовов по стадиям), чтобы себестоимость и качество можно было сравнивать.

## 2. Обзор волн

| Волна | Цель | Результат для приёмки | Шлюз |
|---|---|---|---|
| 0 | Фундамент: схема, эталонный набор, окружение | Валидная схема Storyboard, 8 размеченных видео, замеры железа | A |
| 1 | Индексатор | `razkadr index <файл или ссылка>` даёт кадры, транскрипт, OCR, эмбеддинги; известна стоимость минуты | B |
| 2 | Отбор | `razkadr select` даёт Storyboard-черновик без текста; метрики поиска | C |
| 3 | Текст | Storyboard с текстом (RU/EN), правки сохраняются | D |
| 4 | Раскладка и экспорт | `razkadr build` даёт PPTX, PDF, Google Slides, HTML, JSON | E |
| 5 | Приёмка ядра MVP | Слепая проверка на новых видео, отчёт о себестоимости | F |
| 6+ | Веб-оболочка, второй пресет, интеграции | после шлюза F | — |

Зависимости: `0 → 1 → 2 → 3 → 4 → 5`. Внутри волн возможен параллелизм (отмечен в таблицах).

## 3. Волна 0 — Фундамент

Цель: зафиксировать контракты и измерительную базу, чтобы остальное строилось на фактах.

| № | Наряд | Размер | Зависит | Контракт (вход → выход) |
|---|---|---|---|---|
| 001 | Каркас репозитория, CI, процесс | S | — | пустой репозиторий → `pytest` и `ruff` зелёные в CI (**сделан в первом коммите**) |
| 002 | JSON Schema Storyboard v1.0, валидатор, примеры | M | 001 | `storyboard.json` → `razkadr validate` возвращает ok/ошибки с путём; 3 примера (валидный, с правками, невалидный) |
| 003 | Эталонный набор рецептов и формат разметки | M | 001 | 8 видео + `labels/*.json` (hero, ингредиенты, 5–8 шагов с таймкодами) → `razkadr eval-check` подтверждает целостность набора |
| 004 | Выбор провайдеров API: условия, замеры задержки и стоимости | M | 001 | ключи кандидатов + 1 минута тестового видео → `docs/providers.md` (задержка и стоимость ASR, эмбеддингов, VLM, LLM на 1 минуту) и ADR-0004 об условиях провайдеров и BYOK |

**Состав эталонного набора (наряд 003):** 8 видео, 3–15 минут: 2 с русской озвучкой, 2 с английской, 2 без речи с экранными подписями, 1 без речи без текста, 1 «плохого» качества (ручная съёмка, свет). Для каждого вручную размечены: кадр готового блюда, кадр ингредиентов, 5–8 ключевых шагов (таймкод ±2 с допускается). Видео берутся по ссылкам (YouTube, TikTok и др.) и скачиваются локально; ссылка, дата и условия использования фиксируются в `data/eval/SOURCES.md`, локальная копия хранится вне git (ссылки могут пропасть).

**Параллелизм:** 002, 003, 004 независимы после 001.

### Шлюз A — «Контракты и измерительная база готовы»

| Критерий | Как проверяется |
|---|---|
| Схема Storyboard валидирует 2 валидных примера и отклоняет невалидный с указанием пути ошибки | `pytest tests/test_schema.py` |
| В схеме предусмотрены `user_edited`, `alternatives`, три режима текста, языки (`source_lang`, `output_lang`) | ревью владельцем |
| Эталонный набор: 8 видео размечены, источники зафиксированы | `razkadr eval-check` + `SOURCES.md` |
| Провайдеры-кандидаты подключены; замерены задержка и стоимость ASR, эмбеддингов, VLM, LLM на 1 минуте видео | `docs/providers.md` |
| Условия провайдеров (коммерческое использование, хранение и обучение на данных, лимиты) проверены, решение записано | ADR-0004 |

**No-go если:** разметка эталона неполная (метрики волны C будут недостоверны) или нет рабочих API-ключей провайдеров для замеров.

### Шлюз B — «Индекс строится, и он полезен»

| Критерий | Как проверяется |
|---|---|
| `razkadr index` отрабатывает на **8/8** видео набора без ручных правок (минимум 3 видео индексируются по ссылке, остальные по файлу) | прогон + `run.json` |
| **Полнота кандидатов кадров:** для ≥ 95 % эталонных кадров (hero, ингредиенты, шаги) среди извлечённых кадров есть кадр в пределах ±2 с | скрипт на эталонном наборе (предложено) |
| Дубликаты и смазанные кадры отсеяны: доля отброшенных кадров и ручная выборка 50 кадров без явного брака ≥ 90 % | отчёт + ревью |
| Транскрипт: язык определён верно на 8/8 видео; для видео с речью измерена WER на 2-минутных фрагментах | отчёт (порог WER задаётся по результату) |
| OCR: на видео с экранными подписями найдено ≥ 80 % слов списка ингредиентов | ручная сверка на 2 видео (предложено) |
| Замерены время и **стоимость API** обработки 1 минуты видео по стадиям и провайдерам; допустимый порог стоимости задаёт владелец по этим данным | `run.json` → таблица в `docs/acceptance/wave-1.md` |
| Повторный запуск не делает платных вызовов и выполняется ≥ 5× быстрее благодаря кэшу | сравнение времени и счётчиков вызовов (предложено) |
| Смена провайдера ASR или эмбеддингов выполняется правкой конфига; ключи не попадают в логи и артефакты | тест + проверка артефактов |

**Демонстрация владельцу:** просмотр папки кадров и транскрипта одного видео; таблица времени по стадиям.
**No-go если:** полнота кандидатов < 95 % (поиск не сможет найти то, чего нет), затем наряды на сцены/прореживание в той же волне.

## 5. Волна 2 — Отбор

Цель: по описанию и пресету находить лучшие кадры и эпизоды. Главная проверка гипотезы проекта.

| № | Наряд | Размер | Зависит | Контракт |
|---|---|---|---|---|
| 012 | Гибридный поиск: векторы кадров + векторы текста + ключевые слова, RRF | M | 010 | запрос «готовое блюдо» + индекс → ранжированный список кадров с `score_parts` |
| 013 | Пресет `recipe` v1: роли, профиль скоринга (YAML) | M | 002 | `presets/recipe.yaml` загружается и валидируется; роли: hero, ingredients, prep, steps, serving |
| 014 | Выбор эпизодов: пресет + индекс → Storyboard-черновик без текста | L | 012, 013 | `razkadr select runs/<id> --preset recipe` → `storyboard.json` (валидный, с `alternatives`) |
| 015 | Eval-харнесс: метрики top-k, отчёт, сравнение моделей/режимов | M | 003, 012 | `razkadr eval` → таблица: hit@1/@3 по ролям, для каждой конфигурации |
| 016 | Решение по подходу к эмбеддингам (ADR-0002) | S | 015 | результаты сравнения мультимодальных эмбеддингов и «VLM-описание + текст» (с учётом стоимости минуты) → ADR с данными |

**Параллелизм:** 012 и 013 параллельно; 015 можно начинать после 012.

### Шлюз C — «Гипотеза подтверждена или нет»

| Критерий | Как проверяется |
|---|---|
| **hit@3 ≥ 80 %** для ролей hero и ключевых шагов на эталонном наборе (из ТЗ) | `razkadr eval` |
| hit@3 для ролей ingredients не ниже 70 % (предложено; у немых видео зависит от OCR) | `razkadr eval` |
| Проведено сравнение: текст-only vs кадры-only vs гибрид (RRF); минимум 2 подхода или провайдера эмбеддингов, с указанием стоимости минуты видео | таблица в `docs/acceptance/wave-2.md` |
| Подход к эмбеддингам выбран, ADR-0002 принят с данными | ADR |
| Storyboard-черновик валиден по схеме на 8/8 видео | `razkadr validate` |
| Ревью владельцем: для 3 видео выбранные кадры выглядят «пригодными для презентации» | демонстрация (простая HTML-галерея выбора) |

**No-go (ключевое решение проекта):** hit@3 < 80 % по hero и шагам. Разбор: что именно не находится (стили видео? роли?). Варианты: доработка скоринга, VLM-описания кадров на этапе индексации, смена модели. Если после двух итераций порог не достигнут — пересмотр сценария и объёма проекта до траты на волны 3–4.

## 6. Волна 3 — Текст

Цель: к каждому эпизоду кратко, точно и на нужном языке.

| № | Наряд | Размер | Зависит | Контракт |

| 018 | Перевод RU↔EN и нормализация единиц (cup → г/мл, °F → °C по настройке) | M | 017 | `output_lang` → текст на целевом языке; числа, время и температура сохранены |
| 019 | Сохранение правок: `user_edited` не перезаписывается при повторной генерации | S | 017 | правка в JSON + повторный `razkadr text` → правка на месте |
| 020 | Ревью-набор текстов: чек-лист фактов и инструмент сравнения | M | 017 | текст эпизода + оригинал → отчёт по чек-листу (ингредиенты, количества, время, температура) |

**Параллелизм:** 018 и 019 параллельно после 017.

### Шлюз D — «Тексты верны и редактируются»

| Критерий | Как проверяется |
|---|---|
| Ингредиенты: ≥ 90 % позиций и количеств переданы верно (RU→RU, EN→RU, EN→EN) | ручная проверка по чек-листу на 6 видео (предложено) |
| Нет выдуманных фактов: в выборке из 50 текстов не более 2 несоответствий источнику (предложено) | ревью |
| Числа, время, температуры точны в 100 % проверенных случаев | проверка |
| Описания немых сцен (`described`) приемлемы для владельца на 2 немых видео | демонстрация |
| Правки пользователя сохраняются после регенерации (тест) | `pytest` |
| Длина текста эпизода укладывается в лимит макета (1–2 предложения для шага) | автоматическая проверка |

**No-go если:** ошибки в количествах и числах выше порога. Для рецептов это критично, поэтому возможны жёсткие меры (режим `verbatim` по умолчанию для чисел).

| Владелец оценивает каждую презентацию (шкала 1–5 по: выбор кадров, точность текста, оформление); средняя ≥ 4 (предложено) | анкета в `docs/acceptance/wave-5.md` |
| Время «видео → презентация» и стоимость минуты измерены и зафиксированы | `docs/cost.md` |
| Инструкция запуска работает на чистой машине | проверка |
| `limitations.md` честно перечисляет известные слабости | ревью |
| Решения по волне 6+ приняты (см. ниже) | протокол |

**Решения на шлюзе F:** (1) веб-оболочка сразу или улучшение качества; (2) второй пресет и рынок (UX-исследования, вебинары, инспекции); (3) цены и тарифы по реальной себестоимости; (4) состав провайдеров по качеству и цене; условия BYOK и тарифы.

## 9. Волны 6+ (обозначены, детализируются после шлюза F)

| Волна | Содержание |
|---|---|
| 6 | Веб-оболочка: загрузка, очередь, редактор Storyboard, превью слайдов, аккаунты |
| 7 | Монетизация: кредиты, тарифы, платёжный провайдер |

| 9 | Экспорт и интеграции: DOCX, MP4-фрагменты, Notion/Obsidian, публичные ссылки |
| 10 | Команды, API, white-label, масштабирование |

## 10. Реестр рисков по волнам

| Риск | Где проявится | Ответ |
|---|---|---|
| Разметка эталона слабая или односторонняя | шлюзы A, C | второй разметчик на 2 видео, измерить согласованность |
| Не находятся «ингредиенты» у немых видео | шлюз C | OCR и VLM-описание кадров в индексе |
| Условия провайдера API ограничивают сценарий (коммерция, хранение данных, обучение на данных) | шлюз A | ADR-0004, проверка условий, смена провайдера через слой провайдеров |
| Скачивание по ссылкам нарушает условия платформ или права авторов; ссылки ломаются, загрузчики блокируются | шлюзы A, B | локальный режим для внутренней оценки, фиксация источников, копии вне git; для хостед-сервиса решение отдельным ADR-0005 |
| Стоимость API на минуту видео слишком велика | шлюз B | отбраковка кадров до платных вызовов, кэш, пакетные вызовы, BYOK |
| Кадры и аудио уходят третьим сторонам | шлюз E и далее | согласие пользователя, список провайдеров, выбор провайдера |
| Ошибки в количествах при переводе | шлюз D | режим `verbatim` для чисел, чек-лист фактов |
| Расхождения PPTX → Google Slides / PDF | шлюз E | один эталонный шаблон, визуальные тесты, перечень расхождений |
| Рост объёма из-за «всё сразу» | все | не добавлять форматы и пресеты до шлюза F |
