# План реализации Razkadr

Статус документа: v2, 2026-10-15. Основа: [spec.md](spec.md) v0.5. Процесс: [../PROJECT_SCHEME.md](../PROJECT_SCHEME.md).

## 0. Как читать план

- **Наряд** — атомарная (номер наряда = номер GitHub issue) задача с контрактом. Размер: S (до дня), M (несколько дней), L (до недели и больше). Это ориентир сложности, а не обещание по срокам: реальные сроки уточняются после замеров на волне 0.
- **Волна** — группа нарядов с единой целью. Следующая волна стартует только после **шлюза** (приёмки) предыдущей.
- **Шлюз** — проверяемые критерии и демонстрация владельцу. Результат записывается в `docs/acceptance/wave-N.md` по шаблону `docs/acceptance/TEMPLATE.md`. Решение: **go / go с замечаниями / no-go**.
- Пороговые значения помечены «предложено»: их можно корректировать на предыдущем шлюзе, но только осознанно и с записью в протокол.
- Подробно расписаны волны 0–5 (ядро до MVP-результата). Волны 6+ только обозначены и детализируются после шлюза F.

## 1. Сквозные принципы

1. **Контракт раньше кода.** Схема Storyboard и формат разметки эталона фиксируются в волне 0.
2. **Метрики раньше сравнений.** Любое «лучше» (модель, поиск, скоринг) подтверждается на размеченном наборе, не «на глаз».
3. **Python-only до веб-оболочки** (ADR-0001). Металогос не является зависимостью.
4. **Модели только внешние (API), с поддержкой BYOK** (ADR-0004). Локальных моделей нет; на CPU остаются ffmpeg, детекция сцен, хэши и рендер. Платные вызовы выполняются после дешёвой отбраковки и кэшируются.
5. **Минимум реализаций за полными контрактами:** 1 пресет (`recipe`), 2–3 макета, 2 языка вывода (RU, EN).
6. **PPTX — мастер-формат** (ADR-0003): PDF и Google Slides получаются из него.
7. **Воспроизводимость и учёт стоимости:** каждый запуск пишет `run.json` (провайдеры и версии моделей, параметры, время и стоимость вызовов по стадиям), чтобы себестоимость и качество можно было сравнивать.

## 2. Обзор волн

| Волна | Цель | Результат для приёмки | Шлюз |
|---|---|---|---|
| 0 | Фундамент: схема, эталонный набор, окружение | Валидная схема Storyboard, 8 размеченных видео, замеры железа | A |
| 1 | Индексатор | `razkadr index <файл или ссылка>` даёт кадры, транскрипт, OCR, эмбеддинги; известна стоимость минуты | B |
| 2 | Отбор | `razkadr select` даёт Storyboard-черновик без текста; метрики поиска | C |
| 3 | Текст | Storyboard с текстом (RU/EN), правки сохраняются | D |
| 4 | Раскладка и экспорт | `razkadr build` даёт PPTX, PDF, Google Slides, HTML, JSON | E |
| 5 | Приёмка ядра MVP | Слепая проверка на новых видео, отчёт о себестоимости | F |
| 6+ | Веб-оболочка, второй пресет, интеграции | после шлюза F | — |

Зависимости: `0 → 1 → 2 → 3 → 4 → 5`. Внутри волн возможен параллелизм (отмечен в таблицах).

## 3. Наряды и шлюзы

Полные контракты — в `docs/naryady/` и в GitHub Issues. Критерии шлюзов — в файлах `docs/naryady/042…047-gate-*.md`. Волны 3–5 помечены `draft`: контракты уточняются аудитором после предыдущего шлюза.

Исполнитель: `agent` — кодирует агент; `human` — владелец; `both` — агент готовит, владелец обеспечивает ключи/решения.

Критерии шлюза:
- `razkadr index` проходит на 8/8 видео эталонного набора без ручных правок (минимум 3 по ссылке)
- Полнота кандидатов кадров ≥ 95 % эталонных кадров в пределах ±2 с
- Выборка 50 кадров: брак (дубли, смаз) не более 10 %
- Язык определён верно на 8/8; WER измерена на 2-минутных фрагментах
- OCR: ≥ 80 % слов списка ингредиентов на 2 видео с подписями
- Время и стоимость API на минуту видео по стадиям измерены; порог стоимости задаёт владелец
- Повторный запуск без платных вызовов и ≥ 5× быстрее
- Смена провайдера правкой конфига; ключи отсутствуют в логах и артефактах
- ADR-0006 принят владельцем; ADR-0007 рассмотрен

**No-go:** Полнота кандидатов < 95 %; тогда доработка нарядов №6/№9 в той же волне. Блокируется отсутствием наряда №40 (эталонный набор).

## 5. Реестр рисков по волнам

| Риск | Где проявится | Ответ |
|---|---|---|
| Разметка эталона слабая или односторонняя | шлюзы A, C | второй разметчик на 2 видео, измерить согласованность |
| Не находятся «ингредиенты» у немых видео | шлюз C | OCR и VLM-описание кадров в индексе |
| Условия провайдера API ограничивают сценарий (коммерция, хранение данных, обучение на данных) | шлюз A | ADR-0004, проверка условий, смена провайдера через слой провайдеров |
| Скачивание по ссылкам нарушает условия платформ или права авторов; ссылки ломаются, загрузчики блокируются | шлюзы A, B | локальный режим для внутренней оценки, фиксация источников, копии вне git; для хостед-сервиса решение отдельным ADR-0005 |
| Стоимость API на минуту видео слишком велика | шлюз B | отбраковка кадров до платных вызовов, кэш, пакетные вызовы, BYOK |
| Кадры и аудио уходят третьим сторонам | шлюз E и далее | согласие пользователя, список провайдеров, выбор провайдера |
| Ошибки в количествах при переводе | шлюз D | режим `verbatim` для чисел, чек-лист фактов |
| Расхождения PPTX → Google Slides / PDF | шлюз E | один эталонный шаблон, визуальные тесты, перечень расхождений |
| Рост объёма из-за «всё сразу» | все | не добавлять форматы и пресеты до шлюза F |

## 6. Ближайшие действия

1. Агент берёт наряды волны 0 по порядку зависимостей (см. issues, веха «Волна 0»); аудитор принимает PR по `docs/AUDIT.md`.
2. Владелец параллельно: выдаёт API-ключи кандидатов (наряд №4), собирает эталонный набор (наряд №40). Они блокируют только шлюзы A/B/C, не разработку на фикстурах.
3. Владелец позже: OAuth-клиент Google (наряд №25), 3 новых видео для слепой приёмки (наряд №32).
