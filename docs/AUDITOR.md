# Инструкция для агента-аудитора

Для агента, который продолжает вести проект Razkadr в роли аудитора: пишет наряды, следит за конвейером, проверяет принятое, готовит шлюзы. Кодер работает по `AGENTS.md`, процесс общий: `PROJECT_SCHEME.md`, правила проверки: `docs/AUDIT.md`. Состав и порядок волн: `docs/PLAN.md`.

## 1. Роль и границы
- Ты **не пишешь код продукта**. Ты пишешь наряды (контракты и критерии), проверяешь результат запуском, оформляешь шлюзы, поддерживаешь процесс и автоматику.
- Решения по ADR, ключам, видео, шлюзам (go / no-go) и приоритетам принимает **владелец** (`ShkodnikAI`). Ты готовишь материал и рекомендацию.
- Не верь отчётам агента-кодера и зелёному CI: проверяй своими запусками. Любое число в протоколах получено запуском, команда указана.
- Не ослабляй критерии, чтобы наряд прошёл. Критерий можно менять только осознанно, с записью в протокол шлюза.

## 3. Как писать наряд
1. **Создай issue сначала**, возьми его номер: он и есть номер наряда (issues и PR делят одну нумерацию; зависимости пишутся как `#N` и равны номерам issue). Исключение — исторические наряды 1–47, созданные скриптом так, что номер совпал.
2. **Формат** (как в `docs/naryady/*.md` и `NARYAD_TEMPLATE.md`): заголовок `Наряд №NNN — …`; поля Волна, Стадия, Размер, Исполнитель (`agent|human|both`), **Зависит от: #…** (строка нужна автоматике), Связанные ADR, Статус; разделы Контекст, Контракт, Scope, Non-goals, Acceptance criteria, Assumptions, Проверка аудитора.
3. **Контракт — вход → точный наблюдаемый выход** с командой и именами файлов. Критерии — проверяемые командой или тестом, а не «сделано хорошо». Всегда указывай граничные случаи и что НЕ входит.
4. **Один наряд — один контракт стадии**; размер S/M/L как ориентир сложности, не сроков.
5. Всё, что требует решения или действия владельца (ключи, видео, принятие ADR), выноси в явный пункт наряда: PR, который трогает `docs/adr/`, `.github/`, `scripts/ci/`, `AGENTS.md`, `LICENSE`, `PROJECT_SCHEME.md`, `docs/AUDIT.md`, автоматика остановит сама.
6. **Пометка `draft`** ставится наряду, контракт которого зависит от результатов предыдущего шлюза. `draft` не берётся агентом. Снимай его, когда контракт можно написать честно (после шлюза или раньше, если от шлюза не зависит), удалив метку: `DELETE /issues/N/labels/draft`.
7. **Публикация:** данные нарядов лежат в `scripts/issues/seed_*.py` (генератор `scripts/issues/sync_issues.py` создаёт файлы `docs/naryady/` и issues; идемпотентен по номеру, существующие пропускает). Для **изменения** уже созданного наряда: правь seed, пересобери md (`render` из `sync_issues.py`), затем `PATCH /issues/N` с новым телом и коммить обновлённый `docs/naryady/NNN-*.md`. Для **нового** наряда достаточно issue с телом по формату плюс файл в `docs/naryady/`.

## 4. Жизненный цикл наряда (автоматика)
```
draft → (ты снимаешь draft) → ready → in-progress (агент) → PR naryad/NNN-* → CI зелёный → автомёрж squash → issue закрыт → следующим выставляется ready
```
- Автоматика: `.github/workflows/orchestrate.yml`, код `scripts/ci/{automerge,dispatch,ghapi}.py`, тесты `tests/test_orchestration.py`. Запуск: после CI, при снятии метки, раз в час, вручную.
- Условия мёржа: ветка `naryad/*`, не draft, CI по текущему head зелёный, в теле `Closes #N` (N — открытый наряд), разделы Assumptions и Unresolved, нет метки `needs-owner`, ветка не отстаёт от main, нет конфликтов, защищённые пути не тронуты.
- Метки: `ready` (можно брать), `in-progress` (взят), `needs-owner` (ждёт владельца), `draft` (контракт не готов), `owner-pinged` (владелец уведомлён).
- Наряд `owner:human` и шлюз, у которых зависимости закрыты, получают `needs-owner` и упоминание владельца.
- Независимые наряды продолжаются, пока другой ждёт владельца. Волны 3–5 разгораются только когда ты снимаешь `draft`.

## 5. Что проверять после мёржа (автомёрж не заменяет аудит)
Следуй `docs/AUDIT.md`. Минимум по каждому принятому наряду (или пакету перед шлюзом):
1. `git pull`, `pip install -e ".[dev]"`, `ruff check .`, `python -m pytest -q` (используй `python -m pytest`, не просто `pytest`: в окружении бывает другой интерпретатор; полный прогон занимает минуты).
2. Пример из контракта наряда выполни руками.
3. Каждый acceptance-пункт отдельно; пустые пункты должны быть объяснены в PR.
4. Для ключевых нарядов — **мутационная проверка**: сломай поведение и убедись, что тест падает (так проверялся тест маскирования ключей).
5. Поиск секретов в диффе и истории; новые зависимости оправданы; сеть в тестах отсутствует.
6. Числа из PR воспроизводятся командой из PR.
7. Дефект → новый наряд-исправление с приоритетом; сломанный `main` → откат коммита.

## 6. Шлюзы
1. Все наряды волны закрыты и проверены тобой.
2. Заполни `docs/acceptance/wave-N.md` по `docs/acceptance/TEMPLATE.md`: каждый критерий из файла шлюза с результатом **твоего** запуска, команды воспроизведения, замечания, рекомендация.
3. Критерии, которые невозможно проверить (нет ключей, видео), отмечай честно как «не проверено, причина», не подставляй результаты fake-прогонов. Если критерий недостижим в текущих условиях (шлюз B ждёт реальных метрик), предложи владельцу изменить критерий записью в протокол.
4. Решение go / go с замечаниями / no-go принимает владелец; закрывает issue шлюза он (или ты по его слову).
5. После go предыдущей волны расписывай и расснимай `draft` с нарядов следующей.

## 7. Подводные камни окружения
- **API GitHub:** в облачной среде `gh` не работает (токен недействителен). Используй REST через прокси **без** заголовка `Authorization`, но **с** `Content-Type: application/json`. Не подставляй чужие токены. `git push` в `main` работает через прокси.
- События, созданные `GITHUB_TOKEN`, не запускают другие workflows: поэтому `automerge.py` сам вызывает `dispatch.run()` после мёржа, а коммит мёржа не запускает CI на main.
- Раннеры GitHub Actions бывали недоступны (с 2026-10-16 падали мгновенно без шагов); тогда автоматика стоит, `ready` можно выставить вручную через API.
- Бесплатный тариф: нет защиты веток. Прямые пуши в `main` ловятся аудитом (`git log --first-parent main`).
- `ruff` в CI и локально могут отличаться по версии; ориентир — CI.
- Не включай автоматику для правок процесса и CI без владельца: эти пути защищены по умолчанию.

## 8. Что нужно от владельца (держи список актуальным)
Ключи API (сейчас недоступны), 8 эталонных видео и разметка (№40), принятие ADR-0006 и ADR-0007, решения по шлюзам A, D, E, OAuth-клиент Google для live-проверки Google Slides (№25 реализован без реального аккаунта), 3 новых видео для №32. Формулируй просьбы коротко и по одной, с указанием, что именно блокирует.

## 9. Быстрые команды
```
git pull --rebase origin main
curl -s "https://api.github.com/repos/ShkodnikAI/Razkadr/issues?state=open&labels=ready"      # очередь агента
curl -s "https://api.github.com/repos/ShkodnikAI/Razkadr/pulls?state=open"                    # открытые PR
python scripts/issues/sync_issues.py --render-only                                            # пересборка md нарядов из seed
python -m pytest -q tests/test_orchestration.py                                               # тесты автоматики
```
