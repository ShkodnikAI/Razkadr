# Конфигурация Razkadr (razkadr.toml)

Документ описывает конфигурацию уровня волны 0: поиск файла, переопределение
через окружение, обработку секретов и разделы слоя провайдеров (наряд №033,
ADR-0004). Ключи никогда не попадают в логи, `run.json` и текст исключений —
это проверено тестами (`tests/test_providers.py`).

## Где лежит файл

Порядок поиска (первый найденный используется, `src/razkadr/config.py`):

1. Явный путь: `razkadr validate --config путь/до/razkadr.toml` (и аргумент `explicit` в API).
2. `./razkadr.toml` — текущий каталог.
3. `~/.config/razkadr/razkadr.toml` — пользовательский.
4. Ничего не найдено — значения по умолчанию (`{"runs_dir": "runs"}`).

## Переопределение через окружение

Любой ключ переопределяется переменной `RAZKADR_<ИМЯ>` (имя ключа
нижним регистром): `RAZKADR_RUNS_DIR=runs2` задаёт `runs_dir`.

Переменные, похожие на секрет (содержат `key`, `token`, `secret`,
`password`), в конфигурацию не попадают вовсе: их значения уходят в реестр
секретов и используются только для маскирования.

## Секреты: два способа передать ключ

| Способ | Как | Когда использовать |
|---|---|---|
| Через переменную окружения | `api_key_env = "ASR_API_KEY"` — в конфиге имя переменной, само значение берётся из окружения | Рекомендуемый способ |
| Прямо в конфиге | `api_key = "..."` — значение удаляется из эффективной конфигурации и хранится в реестре секретов | Режим BYOK (`[keys] mode = "user"`), когда пользователь сам правит свой локальный toml |

Прямые ключи работают на любом уровне вложенности: ключ с секретным именем
удаляется из конфигурации (и из её хэша) ещё при загрузке и сохраняется в
реестре под точечным именем раздела, например `asr.api_key`. Слой
провайдеров достаёт его оттуда при сборке сервиса. Ключ-суффикс `_env`
(`api_key_env`) секретом не считается — это имя переменной, а не секрет.

Маскирование применяется до сериализации (`deep_mask`): значения
прогоняются через реестр секретов в `run.json`, записях кэша и логах,
затем строка целиком маскируется ещё раз — это ловит и «необычные» ключи
с кавычками, regex-метасимволами и не-ASCII символами.

Если ключ объявлен через `api_key_env`, но переменная не задана или пуста,
слой провайдеров падает с понятной ошибкой вида
`export ASR_API_KEY=<your key> (keys are never logged)` — это ошибка
конфигурации, а не сети.

## Разделы провайдеров

Все ML-функции идут через внешние API (ADR-0004); стадия зависит только от
интерфейса, реализация выбирается конфигурацией (наряд №033). Четыре задачи:

| Раздел | Задача | Метод | Стадия по умолчанию |
|---|---|---|---|
| `[asr]` | речь → текст | `transcribe(audio_path, lang)` | `transcript` |
| `[embeddings]` | векторы текста и кадров | `embed_texts`, `embed_images` | `index` |
| `[vlm]` | описание изображения | `describe_image(path, prompt)` | `ocr` |
| `[llm]` | chat completion | `complete(messages)` | `chunks` |

```toml
[asr]
provider = "fake"            # имя реализации, см. FACTORIES в providers/layer.py
model = "fake-nova-2"        # модель; входит в ключ кэша
api_key_env = "ASR_API_KEY"  # или api_key = "..." (не рекомендуется, маскируется)
max_attempts = 3             # повторы при временных ошибках (TransientError)
base_delay_s = 1.0           # задержка: base_delay * 2^(попытка-1)
requests_per_minute = 60     # троттлинг частоты вызовов
max_concurrency = 1          # параллельные вызовы одного провайдера
model_version = "2"          # версия модели; входит в ключ кэша

  [asr.tariff]
  units = "seconds"          # тарифицируемая единица: seconds | tokens | images
  price = 0.0059             # цена за единицу
  currency = "USD"           # валюта учёта — USD (наряд №033)
  tariff_date = "2026-10-01" # дата тарифа; вносится вручную после наряда №4
```

`[embeddings]`, `[vlm]`, `[llm]` настраиваются так же. В волне 0 доступны
только `fake`-реализации (детерминированные, без сети); реальные адаптеры —
наряды №37–39. Смена провайдера — правка `provider` в toml, код стадий
не меняется (покрыто тестом `test_provider_switch_by_config`).

У стадии индекса (наряд №010) есть один собственный ключ в этом разделе:

```toml
[embeddings]
provider = "fake"
model = "fake-embed-v2"
dim = 8                     # только для fake-фабрики: размерность векторов
batch_size = 16             # входов на один вызов API (наряд №010); >= 1
```

`batch_size` ограничивает число кадров/текстов в одном батче: каждый батч
кэшируется слоем провайдеров отдельно (sha256 его входов), поэтому меньший
батч — более мелкое зерно кэша, больший — меньше накладных расходов на
запросы. Изменение `batch_size`, `provider`, `model` или `model_version`
меняет ключ кэша стадии и запускает пересборку индекса (смена модели/провайдера
помечается в логе как `index is stale`). Без раздела `[embeddings]` стадия
индекса пропускается с предупреждением — конвейер остаётся рабочим.

### Реальные адаптеры ASR (наряд №037, ADR-0006)

В `[asr]` доступны реальные реализации: `provider = "gemini"` (по умолчанию
по ADR-0006, модель `gemini-3.5-transcribe`) и `provider = "deepgram"`
(запасной, модель `nova-3`). Ключ передаётся переменной окружения
(`api_key_env`) или прямым `api_key` в локальном toml (режим BYOK, маскируется):

| provider | Модель по умолчанию | Переменная ключа | Единицы учёта |
|---|---|---|---|
| `gemini` | `gemini-3.5-transcribe` | `GEMINI_API_KEY` | секунды аудио |
| `deepgram` | `nova-3` | `DEEPGRAM_API_KEY` | секунды аудио |

```toml
[asr]
provider = "gemini"            # или "deepgram"
model = "gemini-3.5-transcribe"
api_key_env = "GEMINI_API_KEY" # export GEMINI_API_KEY=... вне репозитория
max_attempts = 3
base_delay_s = 1.0
requests_per_minute = 60
max_concurrency = 1

  [asr.tariff]
  units = "seconds"
  price = 0.00005              # ~$0.003/мин; источник: docs/providers.md, 2026-10-16
  currency = "USD"
  tariff_date = "2026-10-16"
```

Оба адаптера берут аудио частями WAV (16 кГц, моно — как готовит стадия
transcript), ключ уходит в заголовке запроса (в URL и сообщениях ошибок его
нет), ответ нормализуется в единый тип `Transcript` (таймкоды в секундах,
язык — первичный тег BCP-47: «ru-RU» → «ru»). Ошибки провайдера
отображаются в таксономию слоя: неверный ключ — `AuthError`, исчерпанная
квота — `QuotaError`, лимит частоты и недоступность (5xx, таймаут) —
`TransientError` (слой повторяет с экспоненциальной задержкой).
Стоимость списывается по секундам аудио: у `deepgram` — по
`metadata.duration` ответа провайдера, у `gemini` — по длительности WAV.

### Реальные адаптеры эмбеддингов (наряд №038, ADR-0006)

В `[embeddings]` доступны реальные реализации: `provider = "openai"`
(текстовый, `text-embedding-3-small` — путь «VLM-описание + текст» по
ADR-0006) и `provider = "cohere"` (мультимодальный фолбэк, `embed-v4.0` —
кадры и текст в одном пространстве):

| provider | Модель по умолчанию | Переменная ключа | Единицы учёта | Лимит батча |
|---|---|---|---|---|
| `openai` | `text-embedding-3-small` | `OPENAI_API_KEY` | токены (`usage.prompt_tokens`) | 2048 |
| `cohere` | `embed-v4.0` | `COHERE_API_KEY` | токены (`meta.billed_units.input_tokens`) | 96 |

```toml
[embeddings]
provider = "openai"            # или "cohere"
model = "text-embedding-3-small"
api_key_env = "OPENAI_API_KEY" # export OPENAI_API_KEY=... вне репозитория
batch_size = 16                # входов на один вызов стадии индекса (наряд №010)
max_batch = 2048               # входов на один HTTP-запрос (потолок провайдера)
# только для cohere:
input_type = "search_document" # тип входа Cohere; поиск ходит тем же сервисом
max_image_dim = 1024           # длинная сторона кадра перед отправкой, px
max_image_bytes = 4000000      # жёсткий предел размера одной картинки, байт
jpeg_quality = 85              # стартовое качество; снижается по лестнице при превышении лимита
```

Адаптер `openai` — только текст: `embed_images` падает с понятной ошибкой
конфигурации (сборка «VLM-описание + текст» — за нарядом №039 / ADR-0002).
Адаптер `cohere` отправляет кадры после даунскейла до `max_image_dim` по
длинной стороне и JPEG-перекодирования; при превышении `max_image_bytes`
качество снижается по лестнице (85→70→55→40), затем сторона уменьшается
вдвое, пока картинка не влезет, — избыточное разрешение провайдер не видит.
Оба адаптера сами режут список входов на батчи `max_batch` и склеивают
результаты. Размерность берётся из ответа провайдера (не константа) и
попадает в манифест индекса (наряд №010/№035); ключ передаётся в заголовке
Authorization, в URL его нет.

### Реальные адаптеры VLM и LLM (наряд №039, ADR-0006)

В `[vlm]` и `[llm]` доступны реальные реализации: `provider = "gemini"`
(по умолчанию по ADR-0006, `gemini-3.5-flash-lite` — описания кадров и OCR)
и `provider = "openai"` (`gpt-6-luna` — чанки, сжатие, перевод). Ключи:
`GEMINI_API_KEY` для `[vlm]`, `OPENAI_API_KEY` для `[llm]`.

```toml
[vlm]
provider = "gemini"
model = "gemini-3.5-flash-lite"
api_key_env = "GEMINI_API_KEY"
json_mode = false             # форсировать JSON-ответ (response_mime_type)
max_image_dim = 1024          # кадр уменьшается перед отправкой (см. [embeddings])
max_image_bytes = 4000000
jpeg_quality = 85

[llm]
provider = "openai"
model = "gpt-6-luna"
api_key_env = "OPENAI_API_KEY"
temperature = 0               # задачи извлечения — детерминированные (наряд №039)
json_mode = false             # response_format json_object + локальная проверка
```

Режим `json_mode = true` заставляет модель отвечать строго JSON и проверяет
ответ локально: невалидный JSON ведёт к повтору запроса (по умолчанию до
2 повторов), затем — к понятной ошибке провайдера. Для `[chunks]` это
совместимо с нарядом №008: после исчерпания повторов стадия уходит в
детерминированный запасной алгоритм. Важно: JSON-mode OpenAI требует, чтобы
слово «JSON» присутствовало в сообщениях (контракт провайдера) — промпты
`prompts/chunking.v1.md` и `prompts/ocr.v1.md` ему удовлетворяют. Учёт:
токены из ответа провайдера (`usageMetadata` у Gemini — промпт включает
токены изображения; `usage.prompt_tokens + completion_tokens` у OpenAI).
Кадры перед отправкой готовит `providers/images.py` (даунскейл + лимит
байтов, как у эмбеддингов). Смена модели внутри вендора — конфигом
(`model = ...`), без правок стадий. Запасные варианты ADR-0006 из другого
вендора (VLM `gpt-6-luna` для OCR, LLM `gemini-flash` для чанков) требуют
своих адаптеров на том же протоколе — при необходимости оформляются
отдельным нарядом (см. Unresolved в PR наряда №039).

Промпты версионированы в пакете (`prompts/<имя>.v<N>.md`); sha256 промпта
записывается в `run.json` (стадии `chunks`/`ocr`) и входит в ключ кэша —
смена версии промпта перезапускает стадию.

### Учёт стоимости

Каждый вызов дописывает запись в `provider_calls` файла `run.json`:
стадия, задача, провайдер, модель, единицы (`seconds`/`tokens`/`images`),
стоимость (`amount`, `currency`, `tariff_date`) и признак `cache_hit`.
Стоимость = сумма единиц тарифицируемого вида × цена, округление до 6
знаков. Без раздела `[<задача>.tariff]` вызов записывается с нулевой
стоимостью и датой-маркером `1970-01-01` — пропуск тарифа виден, а не
молча занижен. Тарифы вносятся владельцем вручную (наряд №4 соберёт реальные).

## Ключи и режимы BYOK

```toml
[keys]
mode = "platform"   # платформенные ключи (по умолчанию) | "user" (BYOK)
```

Режим валидируется при сборке слоя: допустимы `platform` и `user`
(ADR-0004 — модели только внешние, с поддержкой BYOK). В режиме `user`
пользователь передаёт свои ключи (обычно через `api_key_env` или прямой
`api_key` в своём локальном toml); платформа ключей не хранит — хранение
в БД и шифрование вынесены в веб-волны (non-goals наряда №033).

## Кэш вызовов

```toml
[cache]
dir = "~/.cache/razkadr/calls"  # по умолчанию; каталог JSON-записей кэша
```

Ключ кэша — sha256 канонического JSON от задачи, имени провайдера, модели,
`model_version` и всех входов/параметров. Повторный вызов с теми же входами
не обращается к провайдеру (счётчик вызовов проверяется тестом), в
`run.json` попадает `cache_hit=true`, стоимость — 0. Записи кэша
маскируются так же, как артефакты.

## Стадия ingest (наряд №005)

```toml
[ingest]
fps = 10                  # потолок частоты кадров (выход CFR)
max_height = 1080         # потолок высоты, px (ширина по аспекту, чётная)
max_duration_s = 3600     # отказ, если источник длиннее
max_file_size_mb = 2048   # отказ, если источник больше
```

`razkadr index <файл|URL>` приводит видео к единому формату (mp4, mpeg4,
AAC при наличии звука), извлекает `audio.wav` (16 кГц, моно, PCM) и пишет
`source.json` (валиден схеме `source.v1.json`). Файл без звуковой дорожки
— не ошибка: `audio.wav` не пишется, в `streams` просто нет аудио-записи.
Версии ffmpeg и yt-dlp попадают в `tool_versions` файла `run.json` (схема
run.v1 отводит это поле внешним инструментам) и входят в ключ кэша стадии:
смена инструмента или лимитов перезапускает стадию.

## Стадия frames (наряд №006)

```toml
[frames]
scene_threshold = 12.0     # порог ContentDetector (разница кадров HSV)
min_scene_len_s = 0.5      # склейки ближе этого интервала игнорируются
step_s = 2.5               # шаг равномерной выборки, с
dup_threshold = 6          # дистанция Хэмминга pHash, не более которой кадр — дубль
sharpness_threshold = 0.28 # ниже — кадр помечается rejected: blurry
jpeg_quality = 90          # качество *.jpg в runs/<id>/frames/
```

После ingest стадия frames набирает кандидатов (середина каждой сцены по
PySceneDetect плюс равномерная сетка `step_s`), считает для каждого
резкость (нормированная дисперсия Лапласиана), pHash и экспозицию,
и пишет `frames.json` (схема `frames.v1.json`) и `frames/*.jpg`.
Кадры не удаляются: дубли (дистанция pHash до принятого кадра своей или
соседней сцены ≤ `dup_threshold`) и размытые (резкость ниже порога)
помечаются `rejected: true` с причиной `reject_reason`, файлы остаются.
Пороги подобраны на фикстурах наряда №034 (замеры: склейки дают score
21.45–34.05 при шуме внутри сцены ≤ 0.60; резкость размытого фрагмента
0.206–0.212 против 0.909–0.977 у чётких; дистанция pHash внутри сцены 0,
между соседними сценами ≥ 8) и будут пересматриваться после эталонного
набора (шлюз B). Версия scenedetect входит в `tool_versions` и в ключ
кэша стадии; повторный запуск на том же видео даёт байт-в-байт тот же
`frames.json`.

## Стадия transcript (наряд №007)

```toml
[transcript]
lang = ""            # принудительный язык (BCP-47, например "ru"); пусто — автоопределение провайдером
part_length_s = 120  # максимальная длина одной части аудио, с
overlap_s = 2        # перекрытие соседних частей, с (строго меньше part_length_s)
```

После frames стадия transcript превращает `audio.wav` в `transcript.json`
(схема `transcript.v1.json`) через слой провайдеров: реализация выбирается
в `[asr]`, стадия знает только интерфейс `transcribe(audio_path, lang)`.
Длинное аудио режется на части `part_length_s` с перекрытием `overlap_s`
(срезы — стандартным модулем `wave`, без потерь; части лежат в
`runs/<id>/audio_parts/`), каждая часть уходит в ASR отдельным вызовом.
При склейке сегменты смещаются на смещение части, сортируются по времени;
сегмент поздней части, начавшийся в зоне перекрытия, отбрасывается, если
пересекается по времени с уже принятым сегментом и тексты похожи
(нормализация пробелов и регистра, вхождение для обрезанных на стыке
фраз или схожесть от 0.8). Сегменты с разным текстом в зоне перекрытия
сохраняются — содержимое не теряется.

Язык: провайдер определяет сам (`lang = ""`) или задаётся принудительно;
язык артефакта — самый частый среди частей, при равенстве — язык первой
части. Источник без звуковой дорожки — не ошибка: пишется валидный пустой
транскрипт (`lang: "und"`, без сегментов) без единого вызова провайдера;
тот же результат даёт аудио без распознанной речи.

Ключ кэша стадии: sha256 `audio.wav` + параметры `[transcript]` +
провайдер/модель/`model_version` из `[asr]` — смена провайдера или
конфига перезапускает стадию. Каждый вызов тарифицируется секундами
аудио через `[asr.tariff]` и попадает в `provider_calls` файла `run.json`
с признаком `cache_hit`.

## Стадия chunks (наряд №008)

```toml
[chunks]
method = "llm"       # llm (по умолчанию) | fallback — детерминированная разбивка без LLM
max_chars = 1200     # предел длины чанка в символах
pause_s = 1.5        # пауза между сегментами, закрывающая чанк (запасной алгоритм)
```

После transcript стадия chunks группирует сегменты `transcript.json`
в тематические чанки `chunks.json` (схема `chunks.v1.json`: `id`,
`t_start`, `t_end`, `text`, `lang`, `segment_ids` — привязка к сегментам
транскрипта по 0-индексам). При `method = "llm"` границы чанков
выбирает LLM из `[llm]`: промпт версионирован и лежит в пакете
(`prompts/chunking.v1.md`), ответ — только JSON вида
`{"boundaries": [0, 2, 5]}` с индексами сегментов, начинающих новый
чанк. LLM не пишет текст чанков: текст, таймкоды и язык собираются из
самого транскрипта, поэтому чанки никогда не режут сегмент посередине,
покрывают транскрипт без пропусков и перекрытий, и конкатенация чанков
равна транскрипту. Температура 0 и фиксированный JSON-формат — настройка
реального адаптера (наряд №039); fake-провайдер детерминирован и так.

Невалидный ответ LLM (не JSON, неверные границы, чанк из нескольких
сегментов длиннее `max_chars`) — не ошибка: используется запасной
детерминированный алгоритм (по паузам `pause_s` и длине `max_chars`),
причина попадает в лог предупреждением. Запасной путь — единственный,
когда `method = "fallback"` или секция `[llm]` не задана вовсе;
настроенный, но сломанный LLM (неизвестный провайдер, ключ, auth/quota)
падает с ясной ошибкой — явная конфигурация не должна деградировать
молча. Транскрипт без сегментов даёт валидный пустой `chunks.json` без
вызовов провайдера. Один сегмент длиннее `max_chars` становится чанком
целиком: сегменты не режутся посередине.

Ключ кэша стадии: sha256 `transcript.json` + параметры `[chunks]` +
провайдер/модель/`model_version` из `[llm]`. Вызов LLM тарифицируется
токенами через `[llm.tariff]` и попадает в `provider_calls` с признаком
`cache_hit`.

## Стадия ocr (наряд №009)

```toml
[ocr]
max_ocr_frames = 60          # потолок вызовов провайдера; 0 — стадия пропускается
edge_density_threshold = 0.005  # доля граничных пикселей (Canny) в кадре: «вероятно есть текст»
lang = ""                    # принудительный язык результатов (BCP-47); пусто — "und"
```

После chunks стадия ocr ищет экранный текст (списки ингредиентов, шаги,
таймеры) в кадрах из `frames.json` и пишет `ocr.json` (схема
`ocr.v1.json`: `frame`, `t`, `text`, `lang`). Распознавание идёт через
VLM из `[vlm]` (промпт версионирован и лежит в пакете —
`prompts/ocr.v1.md`); стадия знает только интерфейс
`describe_image(path, prompt)`.

OCR не прогоняет все кадры: дешёвый CPU-фильтр отбирает кандидатов —
кадры с плотностью границ не ниже `edge_density_threshold` плюс по
одному ключевому кадру каждой сцены (самый резкий принятый кадр сцены
по метрике `sharpness` из `frames.json`). Кандидаты упорядочены от
самых «текстовых» (плотность по убыванию, затем время) и обрезаны
лимитом `max_ocr_frames` — потолок стоимости. Замеры на фикстурах
наряда №034 (`titles.mp4`, ffmpeg 7.1.5): пустые кадры 0.0000, кадры с
титрами 0.0150–0.0178 → порог 0.005 по умолчанию с запасом ≥ 3×; порог
будет пересматриваться на эталонном наборе (шлюз B). Каждый вызов кэшируется
слоем провайдеров по хэшу кадра и промпта и тарифицируется через
`[vlm.tariff]` в `provider_calls`.

Ответ VLM — только экранный текст построчно (пустой ответ, если текста
нет); стадия чистит пробелы и больше ничему не доверяет. Одинаковый
текст на последовательных отправленных кадрах схлопывается в один
результат, сохраняющий первый кадр серии: `t` — начало интервала
показа, конец ограничен следующим результатом (отдельного `t_end` в
схеме `ocr.v1.json` нет). Сравнение — по нормализованным пробелам, с
учётом регистра: разный текст не схлопывается никогда.

Пустой результат без обращений к провайдеру — валидный исход: лимит 0,
нет принятых кадров или ни один не прошёл фильтр. Секция `[vlm]` не
задана вовсе — стадия пропускается с предупреждением в логе (конвейер
остаётся рабочим, как запасной путь chunks); настроенный, но сломанный
VLM (неизвестный провайдер, ключ, auth/quota) падает с ясной ошибкой.
Детерминированного запасного алгоритма у OCR нет: неверный ответ VLM
молча придумал бы или спрятал экранный текст, поэтому ошибки провайдера
пробрасываются.

Ключ кэша стадии: sha256 `frames.json` + параметры `[ocr]` + sha256
промпта + провайдер/модель/`model_version` из `[vlm]` — смена
провайдера, промпта или конфига перезапускает стадию.

## Стадия text (наряды №017, №018)

```toml
[text]
mode = "auto"        # auto (по умолчанию) | verbatim | condensed | described
default_limit = 180  # лимит символов для ролей без записи в role_limits
output_lang = ""     # целевой язык вывода (наряд №018); пусто = project.output_lang

  [text.units]       # нормализация единиц ДО провайдера (наряд №018); по умолчанию выключена
  fahrenheit_to_celsius = false  # 350 °F -> 177 °C (арифметически, с округлением)
  cup_to_ml = 0                  # 1 cup -> N мл (US cup ~ 240 мл); 0 = не конвертировать

  [text.role_limits] # цели/потолки длины по ролям пресета (в символах)
  hero = 120         # = subheading_max движка раскладки (наряд №021)
  ingredients = 480  # = 12 пунктов x 40 (ingredients_list)
  prep = 120         # = step_text_max (steps_grid)
  steps = 120
  step = 120         # канонический пример (examples/storyboard.*) использует единственное число
  serving = 180      # = caption_max
```

Стадия text заполняет `episodes[].text` черновика Storyboard (наряд №014)
из артефактов запуска и возвращает Storyboard с текстом (схема
`storyboard.v1.json`, поля `text` — наряд №002): `mode`, `source_lang`,
`original`, `output`, `output_lang`. Отчёт стадии — `text.json` в каталоге
запуска: решения по каждому эпизоду (режим, причины отката, длины, лимит)
и предупреждения.

Три режима:

- **verbatim** — дословный транскрипт: сегменты `transcript.json`,
  пересекающиеся с отрезком эпизода `[t_start, t_end]`, целиком, в порядке
  времени. Текст не переписывается — числа сохраняются по построению.
- **condensed** — сжатие исходного текста через LLM из `[llm]` (промпт
  версионирован и лежит в пакете — `prompts/condense.v1.md`; лимит символов
  подставляется в промпт). Ответу LLM слепо не доверяют: он принимается только если
  непуст, сохраняет каждое число оригинала (детерминированная проверка
  инварианта шлюза D: количества, время, температуры) и умещается в лимит
  роли; иначе — откат к verbatim с предупреждением. Валидный, но слишком
  длинный ответ обрезается по границе слова с многоточием и предупреждением.
- **described** — описание кадра через VLM из `[vlm]` (промпт
  `prompts/describe.v1.md`); единственный источник текста для немого
  эпизода. `original` пуст, `output_lang` — язык проекта.

Выбор режима: `mode = "auto"` (по умолчанию) — эпизод с речью в отрезке
→ `condensed`, без речи → `described`; явный `verbatim`/`condensed` на
немом эпизоде откатывается к `described`; явный `described` применяется
и там, где речь есть. Команда `razkadr text <run_dir> --mode verbatim`
переопределяет `[text] mode` для одного запуска.

Деградация — как в chunks (наряд №008): режим condensed без секции `[llm]`
откатывается к verbatim с предупреждением; described без секции `[vlm]`
оставляет эпизод без текста (схема допускает отсутствие `text`) с
предупреждением; настроенный, но сломанный провайдер (неизвестное имя,
ключ, auth/quota) падает с ясной ошибкой — явная конфигурация не деградирует
молча. Правки пользователя священны: эпизоды с `user_edited: true` и уже
заполненным текстом переносятся как есть и не пересоздаются.

Перевод и единицы (наряд №018). Целевой язык: `[text] output_lang`, иначе
`project.output_lang` из самого Storyboard; `razkadr text --output-lang en`
переопределяет для запуска. Когда целевой язык отличается от языка
эпизода (`source_lang`), готовый текст (verbatim или condensed) переводится
через LLM из `[llm]` — промпт `prompts/translate_episode.v1.md`; перевод,
потерявший число или вернувшийся пустым, отбрасывается, остаётся текст на
языке источника с предупреждением; `text.output_lang` честно фиксирует язык
`output` (`translated_to` — в отчёте). Режим `described` не переводится:
VLM сразу пишет на языке проекта. Нормализация единиц — детерминированная,
ДО любого вызова провайдера (`[text.units]`, по умолчанию выключена — числа
не меняются без явной настройки владельца): `350 °F -> 177 °C` арифметически,
`2 cups -> 480 мл` по курсу `cup_to_ml`; применённые конверсии попадают в
отчёт (`units_converted`), инвариант чисел проверяется против
нормализованного `original` — провайдер не может исказить конверсию.

Повторный запуск безопасен: стадия перезаписывает `storyboard.json` в
каталоге запуска (черновик получает текст); пересоздание идемпотентно,
каждый вызов LLM/VLM кэшируется и тарифицируется слоем провайдеров
(наряд №033) в `provider_calls` файла `run.json`.

### Ревью текстов (наряд №020)

```bash
razkadr text-review runs/<id>/storyboard.json --out review.json
# text-review: 2/3 episodes reviewable: ok 1, review 1, fail 1
#   ep-steps (steps, condensed): fail
#     lost:   {"numbers": {"200": 1}, "measures": {"200 g": 1}}
#   ep-serving (serving, described): n/a - no source text to compare
```

Детерминированный чек-лист фактов и инструмент сравнения (без вызовов
провайдеров): по каждому эпизоду с текстом сравниваются `text.original`
и `text.output`. Факты извлекаются регэкспами и сравниваются как
мультимножества (счётчики важны: «2 яйца» и «2 ч. л.» — два вхождения
«2»): числа, температуры (`350 °F`, `180 °C`, «200 градусов»), время
(`15 мин` → `15 min`, EN-формы `minutes`/`hours` нормализуются), меры
массы и объёма (`200 г`, `2 ст. л.`, `1 cup`; RU/EN-варианты единиц
нормализуются). Слова оригинала, отсутствующие в output (наивный
стемминг срезает падежи: «риса» ↔ «рис»), попадают в
`ingredient_candidates` — кандидаты на потерянные ингредиенты; это
метка для человека, не автоматический провал. Статус эпизода: `fail`
— потеряно число/температура/время/мера (нарушен инвариант шлюза D),
`review` — есть кандидаты или добавленные числа (конверсия единиц,
перифраз — решает человек), `ok`, `n/a` — нет исходника (described).
Коды выхода: 0 — все проверяемые эпизоды ok, 1 — есть fail/review,
2 — ошибка файла. JSON-отчёт (`--out`) кладётся рядом со Storyboard
или в произвольный путь; эпизоды `n/a` в счётчик проверяемых не входят.

## Команда build (наряд №028)

`razkadr build video.mp4 --preset recipe --lang ru` — сквозной запуск:
индекс → отбор → текст → раскладка → рендер → HTML → PDF. Пакет
результатов (`deck.pptx`, `deck.pdf`, `deck.html`, `storyboard.json`)
складывается в каталог запуска; `--out-dir PATH` переносит файлы пакета
туда, каталог запуска остаётся с промежуточными артефактами. См.
`docs/artifacts.md` («Пакет команды build»).

- `--preset` — имя пресета (`presets/<имя>.yaml` относительно текущего
  каталога, по умолчанию `recipe`) или явный путь к YAML.
- `--lang ru|en` — язык вывода для подписей слайдов и текстов эпизодов:
  задает `[text] output_lang` (№018) и `project.output_lang` Storyboard;
  без флага действует конфигурация, иначе язык видео.
- `--mode auto|verbatim|condensed|described` — переопределяет `[text] mode`
  для всех эпизодов (как `razkadr text --mode`).
- Кэш и возобновление: индексные стадии кэшируются как в `razkadr index`
  (№011); раскладка/рендер/HTML/PDF кэшируются по фингерпринтам
  содержимого; отбор и текст повторяются идемпотентно (правки
  пользователя сохраняются, вызовы провайдеров — из кэша вызовов).
- Без `soffice` (LibreOffice) в PATH пакет уходит без PDF с
  предупреждением; таймаут экспорта — `pdf_timeout_s` (№024).
